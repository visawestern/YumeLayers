## 1. Вердикт в одном абзаце

Как **инженерная обвязка** — это крепко: Metal-движок численно корректен (2e-8),
backward свёрток сходится с конечными разностями, чекпоинты в safetensors с атомарной
записью и бэкапами, локальный HTTP закрыт по Host/Origin. Как **продукт, ради которого
всё написано** (генерация аниме-сцен по слоям) — не работает и в текущей архитектуре
работать не может: слоёв в Swift-коде нет вообще, «VAE» не является VAE, латентное
пространство не является латентным (сжатие 3×, рецептивное поле 15 px, 47k параметров),
а бюджет вычислений на 5500M несовместим с обучением диффузии с нуля. Ниже — по пунктам.

## 2. Критические дефекты

### C1. Накопитель градиентов складывается с неинициализированной памятью
`ConvTrainer.swift:702-707`

```swift
accGrads = grads.map { g in
    let c = GPUTensor(engine: engine, rows: g.rows, cols: g.cols)  // память НЕ обнулена
    session.addInPlace(c, g)                                        // c += g
    return c
}
```

`GPUTensor.init(engine:rows:cols:)` (`GpuTraining.swift:13-18`) делает `makeBuffer` без
`blit.fill`. Metal не гарантирует нулевое содержимое приватного буфера. Итог: к сумме
градиентов может примешиваться мусор от предыдущих аллокаций.

Коварство в том, что `sanitizeGrads(..., maxNorm: 1.0)` **маскирует** проблему: мусор
клиппируется по норме, обучение не падает в NaN, loss даже слегка убывает — но
направление шага искажено. Это худший класс бага: тихая порча результата.

Фикс: `blit.fill(buffer: c.buf, range: 0..<n*4, value: 0)` перед `addInPlace`
(в `biasRowGrad` для атомарного пути это уже сделано — там про обнуление помнят).

### C2. Батч > 2 при 854×480 — гарантированный OOM (и краш, см. C3)
`ConvTrainer.swift:617-623`

```swift
let vramBudgetFrames = 50% workingSet / (pw*ph*3*4)   // = 868 кадров
let effBatch = min(max(p.batch,1), vramBudgetFrames, 16)
```

Бюджет считается **только по входным кадрам**, а промежуточные буферы не учтены.
Реальный расход на один сэмпл 856×480 (im2col-матрицы + карты + dcols):

| Слой | cols (float) | МБ |
|---|---|---|
| e1 (27×102 720) | 2.77M | 11 |
| e2 (144×25 680) | 3.70M | 15 |
| e3 (288×6 420) | 1.85M | 7 |
| d1 (576×25 680) | 14.8M | 59 |
| d2 (288×102 720) | 29.6M | 118 |
| d3 (144×410 880) | 59.2M | **237** |
| карты + dcols | ~15M | ~95 |
| **Итого / сэмпл** | | **≈ 540 МБ** |

Все 16 сэмплов живут в **одном command buffer** (forward+backward пишутся подряд,
буферы держатся до `waitUntilCompleted`) → **≈ 8.6 ГБ активаций**.
Плюс `GPUFramePool` уже занял 60% рабочего набора = **5.05 ГБ**.
Итого ≈ 13.7 ГБ на карте с 8.18 ГБ. Падение неизбежно.

Практический диапазон: batch 1–2 работает, 4 — лотерея, 8–16 — краш.
UI при этом разрешает до 16 (`main.swift:2343`).

### C3. Любая нехватка VRAM = жёсткий краш
`GpuTraining.swift:16`, `:26`, `:38` и далее — везде `makeBuffer(...)!`.
При исчерпании памяти Metal возвращает `nil` → `force unwrap` → падение процесса
без сообщения. Для приложения, которое часами грузит GPU, это недопустимо.
Нужен `throws`/`optional` + внятное сообщение в журнал и остановка с сохранением чекпоинта.

### C4. «VAE» — не VAE
`ConvGPU.swift:100-141`. Нет ни `mu/logvar`, ни KL-члена, ни репараметризации:
`latent = tanh(p3)`, loss = чистый MSE. Это детерминированный автоэнкодер.

Следствие: **сэмплировать из него нельзя**. Диффузии пришлось бы выучить неявное
распределение латентов, у которого нет простого приора — ровно та задача, которую VAE
и должен был снять. Вся связка «AE → диффузия в латенте → генерация» рассыпается на шаге 2.

### C5. Латент не является латентным пространством
- 3×856×480 = 1 232 640 значений → 64×107×60 = **410 880**. Сжатие всего **3×**.
- Рецептивное поле энкодера: три conv 3×3 stride 2 → **≈15 px**. На кадре 856×480
  каждая латентная ячейка «видит» 1.7% ширины. Это локальный фильтр цвета, не семантика.
- Параметров: **47 107**. Для аниме-сцен это на порядки меньше, чем нужно.

Диффузия в таком пространстве не дешевле пиксельной: 6420 токенов × 64 — это
attention 6420² на каждый слой. Смысл двухстадийной схемы (сжать → диффундировать) теряется.

### C6. Слоёв (фона/объектов/света) в рабочем коде нет
`grep` по `Sources/` не находит ни одного упоминания слоёв, кроме комментариев.
Единственный генератор слоёв — `src/dataset.py:gen_synthetic_frame` (Python, 8 каналов),
и его **не потребляет ни один пайплайн**: Swift-обучение берёт JPEG-кадры из видео.
То есть центральная идея проекта не реализована даже в виде прототипа, а данные для неё
(ground-truth слои) не производятся.

## 3. Серьёзные дефекты

### H1. Буфер возвращается в пул до завершения GPU-работы
`GpuTraining.swift:308-318` — `sumCols` делает `pool.put(work)` сразу после кодирования,
не дожидаясь `end()`. Сейчас безопасно только потому, что ядро `sumcols_kernel`
(`MetalEngine.swift:259-275`) **не использует** буфер `work` (и переменную `chunk` тоже —
мёртвый код). Как только кто-то допишет редукцию — получит тихую порчу данных.
Правильно: складывать в `staged` и возвращать в `end()`.

### H2. `biasRowGrad` создаёт второй command buffer внутри открытой сессии
`GpuTraining.swift:479-493`. Работает, но хрупко: порядок гарантирован только тем,
что основной буфер ещё не закоммичен. Обнуление нужно делать в том же command buffer
через `blit`-энкодер (как в `upload`).

### H3. Перезагрузка VRAM-пула — 64 синхронизации на окно
`ConvTrainer.swift:1785-1837`: `batch = min(n, 16, ...)`, то есть 1024 кадра грузятся
64 порциями, каждая — свой `commit + waitUntilCompleted`. Плюс полное передекодирование
JPEG. Окно меняется каждые 64 шага → регулярные многосекундные провалы.
Комментарий обещает «порциями по 64» — код делает по 16.

### H4. Поля «Ширина»/«Высота» в UI ни на что не влияют
`main.swift:426-427` создаются, но нигде не читаются; `startTraining` жёстко задаёт
`p.width = 854; p.height = 480` (`main.swift:2331-2332`). README при этом обещает
настраиваемое разрешение.

### H5. Галочки «обработано моделью» не появляются никогда
`processedFrames` только заполняется `false` (`main.swift:2185`), нигде не ставится `true`.
Следствия: бейдж ✓ не показывается, `/api/state.processedCount` всегда 0,
режим «Реконструкция» показывает пустые миниатюры для всех кадров, кроме контрольной
выборки (`reconMemory` содержит только её).

### H6. Resume не продолжает, а только перезагружает веса
`ConvTrainer.swift:562-571, 641-644`: эпохи всегда идут с 0. Метаданные `step`/`epoch`
пишутся в чекпоинт (`saveState(step:)`), но **никогда не читаются**. Комментарий
«продолжить ровно с места срыва» вводит в заблуждение.

### H7. Локальный API без токена
`ApiServer.swift:157-212` — авторизации нет. `TESTING_PLAN.md:117` помечает
«POST /api/train с токеном — [x]». Защита Host/Origin реальная и хорошая (CSRF и
DNS-rebinding закрыты), но любой локальный процесс может запустить обучение/извлечение.

### H8. Python-ветка — второй, недоделанный продукт
- `ui/index.html:191` — кнопка «Стоп» с пустым обработчиком, эндпоинта `/api/stop` нет.
- `src/text_encoder.py` + `src/diffusion.py`: CLIP отдаёт 512-мерный вектор,
  а `text_proj = nn.Linear(64, 128)` → `RuntimeError` при включении текста.
  Плюс `MiniTextEncoder` усредняет по batch и возвращает (1, dim) вместо (B, dim).
- `src/trainer.py:61-90`: `latents.pt` кэшируется навсегда — сменил видео, латенты старые.
- `src/trainer.py:35-58`: VAE всегда учится на `SyntheticDataset`, видео игнорируются.
- README заявляет «без PyTorch», но `requirements.txt`, `run.py`, `src/`, `ui/` — это PyTorch-стек.

## 4. Средние дефекты

- `FrameExtractor.findMarker` (`:271-282`) конвертирует `Data` в `[UInt8]` на каждый вызов
  и сканирует буфер с нуля после каждого кадра → квадратичная сложность на чанк.
- Прогресс извлечения: `progress` каждого видео (0…1) подаётся в общий бар как доля
  от всех видео (`main.swift:2124`) → при нескольких файлах бар прыгает назад.
- `log()` создаёт `DateFormatter` на каждую строку (`main.swift:2628`) — дорого при
  сотнях строк в секунду.
- `inputPool[b].copyFrom(frame)` — синхронный blit на кадр, 16 ожиданий GPU за шаг.
- Нет seed: инициализация весов и синтетика на `SystemRandomNumberGenerator`,
  воспроизвести прогон нельзя. Теста на детерминизм нет (и в плане помечен `[ ]`).
- `checkConvGradients` берёт **3 крупнейших** градиента на слой — выборка смещена,
  мелкие градиенты (где и живут ошибки округления/маскирования) не проверяются.
- `readback 1 кадр` = 8.5 мс на 4.9 МБ (≈580 МБ/с) — превью читаются медленно.
- `gradW` использует plain-ядро: 59.6 мс на d3 (432 потока на 1536 ядрах).
  Атомарный/редукционный вариант в коде есть, но отключён — это ~12% сквозного времени.
- `decodeImageRGB` читает `premultipliedLast`, игнорируя альфу → прозрачные PNG темнеют.
- `ui/index.html` не обрабатывает сетевые ошибки: любой сбой сервера = необработанный reject.

## 5. Покрытие тестами — честная картина

Есть три разных «теста», и их легко перепутать:

1. **XCTest** — `Tests/YumeLayersCoreTests/RegressionTests.swift`, **9 методов**:

3. **`check` / `convcheck`** — ручные CLI-проверки GPU-математики (3 варианта matmul,

Что **не покрыто вообще**:

Чего не хватает в первую очередь (по цене/пользе):

2. Тест сходимости: 50 шагов, loss должен упасть на ≥20% — ловит C1 и ошибки lr.
3. Тест «AE vs билинейный down/up» по PSNR — см. §6.
4. Тесты API на случайном порту (401/400/404).
5. Прогон `selftest` + `convcheck` в pre-commit/CI.

## 6. Адвокат дьявола: идея

### 6.1. Что обещано и что сделано

Обещание: «генерация аниме-сцен по слоям (фон → объекты → свет) в латентном пространстве».
Сделано: 47k-параметровый автоэнкодер, который сжимает кадр в 3 раза, + GUI + API.
Слоёв нет, диффузии на Swift нет (только MLP-прототип 32×32 в `GpuTrainer.swift`),
текстового условия нет. Реализовано примерно 10% пути, и это наименее рискованная часть.

### 6.2. Три аргумента, почему «как задумано» не заработает

**(а) Математическая предпосылка неверна.** Смысл «сжать в латент, потом диффундировать»
— уменьшить размерность на 1–2 порядка и увеличить рецептивное поле. Здесь сжатие 3×,
RF 15 px, 64 канала на 107×60. Это не латент, это цветопреобразование. Диффузия по нему
будет стоить как диффузия по картинке, но с потерянными деталями.

**(б) Бюджет вычислений.** Измерено: 152 ГФЛОП/с на matmul, 45 ГБ/с памяти.
Обучение AE: 130k сэмплов × 0.18 с ≈ **6.5 часов** на 3 эпохи — и это только чтобы
получить мутную реконструкцию. Для диффузии на 6420 токенах даже игрушечный DiT
(dim 128, 4 блока) — это ~90 ГФЛОП на forward, ~0.6 с/шаг, 60 шагов сэмплинга = **1 минута
на картинку**, и качество будет соответствовать 47k-параметровому AE, то есть никакое.
Обучение с нуля до чего-то похожего на аниме на этом железе — это порядки 10¹⁹–10²⁰ FLOP,
то есть тысячи GPU-дней. Ограничение не в коде, а в физике.

**(в) Нет данных для слоёв.** Реальные видео не содержат ground-truth слоёв.
`CRITIQUE.md` (итерация 2.3) сам это признал и предложил синтетический рендер —
но рендер остался в Python и не подключён. То есть даже если AE станет идеальным,
обучать «слои» не на чем.

### 6.3. Самый дешёвый способ проверить идею — и его не сделали

Взять один кадр, сжать билинейно в 8 раз и растянуть обратно. Посчитать PSNR.
Сравнить с PSNR вашего AE. Если AE не бьёт билинейный бейзлайн — архитектура
не работает, и это видно за час, а не за три недели обучения.

Сейчас в репозитории единственный артефакт качества — `outputs/conv_ep000.png`:
слева синтетическая сцена, справа **однотонная серая заливка**. Это честно
(1-я эпоха, 20 шагов), но это единственное свидетельство, и оно не в пользу модели.
Ни FID, ни SSIM, ни LPIPS, ни человеческой оценки 20 сэмплов — ничего.

### 6.4. Самоограничение «чистый Swift, без PyTorch»

Это не инженерное решение, а исследовательский риск, замаскированный под принцип:
- нет автодифференцирования → каждая новая архитектура = руками написанный backward
  (уже сейчас 1 838 строк на 6 слоёв);
- нет mixed precision, fused-ядер, cuDNN-подобных примитивов;
- вся экосистема (предобученные веса, CLIP, SD-латенты, метрики) недоступна.

Выигрыш — независимость от зависимостей. Цена — скорость разработки в разы и потолок
качества, который на 5500M всё равно недостижим. Если цель — «своя модель на Metal»,
это надо честно назвать целью; если цель — «генератор аниме», PyTorch+MPS дал бы
результат за неделю.

### 6.5. Что сделано хорошо (без иронии)

- **Metal-движок**: 2.2e-8 против CPU, тайловый matmul, private-буферы, пул буферов.
  Для рукописного кода это очень прилично.
- **Backward свёрток численно верен**: 2.1% на 18 точках, включая stride-2 и col2im.
  Это самая трудная часть, и она сделана правильно.
- **Инженерная гигиена**: safetensors с проверкой NaN перед записью, атомарная запись,
  бэкапы чекпоинтов с защитой от коллизий, валидация длин при чтении, лимиты тела запроса,
  белый список Host/Origin — лучше, чем в большинстве локальных прототипов.
- **Термо-контроль и watchdog-aware батчи**: видно, что приложение реально гоняли
  на живом железе и чинили падения WindowServer.
- **Выделение чистых функций** (`FramePlanner`, `TrainLiveStatus`, `PaginatorLayout`)
  под тесты — правильный инстинкт.
- **UI** действительно аккуратный: пагинатор, живой heartbeat, ETA, состояния «зависло».

Проблема в пропорции: 60% усилий ушло в кокпит, 10% — в двигатель, 0% — в то,
ради чего всё затевалось.

## 10. Перезагрузка 4 ноября 2026: разбор паники и исправление

### Что произошло на самом деле

Паника — не сбой шейдера и не «инструкции не того API». Текст паники:

```
panic(cpu 6): userspace watchdog timeout: no successful checkins
from WindowServer (2 induced crashes) in 120 seconds
Kernel Extensions in backtrace: com.apple.driver.watchdog
```

Это **watchdog по WindowServer**. WindowServer композитит окна на той же
дискретной GPU (Radeon Pro 5500M, `AMDRadeonX6000`), что и обучение. Когда
GPU перестала отвечать, оконный сервер не смог «отметиться» за 120 секунд —
watchdogd выключил машину. Наш процесс при этом не падал: он стоял в
`waitUntilCompleted()` и ждал вечно.

### Хронология по `~/YumeLayers/train.log` и `kern.boottime`

| Время | Что |
|---|---|
| 10:01:59 | старт обучения, батч 1, «пауза 250 мс», «Авто-пауза при перегреве: включена» |
| 10:02:44 → 10:03:24 | 200 шагов за 40 с → **0.20 с/шаг** |
| 10:06:33 → 10:09:13 | 200 шагов за 160 с → **0.80 с/шаг** (в 4 раза медленнее) |
| 10:10:35 | последний чекпоинт, шаг 1500 |
| — | тишина: GPU перестала отвечать, шаг 1600 не залогирован |
| ~10:17:29 | паника watchdogd (120 с без checkin'ов) |
| 10:19:29 | загрузка системы (`kern.boottime`) |

Падение темпа 0.20 → 0.80 с/шаг за семь минут — это троттлинг. Дальше GPU
просто перестала успевать.

### Корневая причина

Пауза 250 мс **не применялась к шагам**. В коде она стояла здесь:

```swift
// щадящий режим: пауза между эпохами, чтобы не перегружать видеокарту
if ep < p.epochs - 1 {
    Thread.sleep(forTimeInterval: pauseMs / 1000)
}
```

`ep < p.epochs - 1` — то есть **один раз между эпохами**, а эпоха это
43 187 шагов. Внутри эпохи стоял жёсткий `Thread.sleep(0.03)` — 30 мс на
кадр 854×480 при 170 мс работы GPU, доля работы ≈ 85%.

`thermalGuard`, который должен был поднимать `pauseMs` при `.serious`,
тоже работал вхолостую: он менял ровно ту переменную, которая применяется
только на границе эпохи. Авто-троттлинг не срабатывал ни разу.

### Про «OpenCL вместо Metal»

В проекте нет ни одной строки OpenCL: шейдеры — это MSL (`#include <metal_stdlib>`),
компилируются в `MTLLibrary` и исполняются через `MTLComputeCommandEncoder`.
Перепутать API здесь негде.

Но интуиция «GPU нагружали неправильно» верна по сути: дело не в наборе
инструкций, а в **режиме нагрузки** — непрерывная работа без слотов
простоя. Для дискретной GPU в ноутбуке это эквивалентно отказу системы
охлаждения: чип успевает нагреться, а драйвер — зависнуть.

### Что исправлено

| | Было | Стало |
|---|---|---|
| **Доля работы** | пауза 250 мс только между эпохами; 30 мс на шаг | `ThermalGovernor`: пауза на **каждом** шаге из фактического времени GPU, доля работы ≤ 55% |
| **Реакция на нагрев** | `thermalGuard` менял `pauseMs`, который не применялся | решение принимается каждый шаг: `targetDuty` 55% → 45% → 30% → 12% по уровню |
| **Признак нагрева** | только `ProcessInfo.thermalState` (запаздывает) | ещё и дрейф времени шага относительно лучшего замера — троттлинг виден раньше, чем thermalState |
| **Зависший GPU** | `waitUntilCompleted()` — ждёт вечно | ожидание с потолком 30 с, затем аварийный выход: лучше упасть нам, чем утащить WindowServer |
| **Реконструкции** | батч 16 без бюджета (≈7.5 ГБ кэшей), пауза только при `.serious` | батч по бюджету активаций, та же доля работы 55% |
| **Пауза между эпохами** | `pauseMs` (могла быть 0) | не меньше 1000 мс на остывание |

## 11. Плавная нагрузка: замеры и что из них следует

### Вопрос

Можно ли дать такую нагрузку, чтобы карта не грелась и не троттлилась —
например, на 85% мощности?

### Ответ: 85% на этой машине не держится. Замерено.

Добавлен инструмент `yume gpuheat <секунды> <доля работы, %>` — он гоняет
**тот же цикл**, что и обучение (forward + backward свёрточного VAE на кадре
856×480), с заданной долей работы и печатает температуру, мощность и время шага.

| Доля работы | Пик температуры | Время шага | Итог |
|---|---|---|---|
| 85% | **74 °C** | 138 → 194 мс (**+40%**) | деградация |
| 75% | 71 °C | 146 → 241 мс (**+65%**) | деградация |
| 65% | 67 °C | 145 → 160 мс (+10%) | почти ровно |
| 60% | 70 °C | 138 → 153 мс (+11%) | почти ровно |

Рабочая точка этой машины — **60–65% доли работы**, а не 85%.

### Важное уточнение к разделу 10

Замеры показали, что **карта не перегревалась**. Даже при 85% доли работы
температура края кристалла дошла только до 74 °C, а потребление держалось
5–18 Вт — при паспортных ~50 Вт у Radeon Pro 5500M. Порог троттлинга у неё
находится в районе 90–100 °C.

Значит паника 4 ноября — **не тепловой троттлинг**, а зависание GPU:
драйвер перестал отвечать, WindowServer не смог отметиться за 120 с.
Температурный контур полезен (машина больше не греется), но защитой от
повтора служит другое — **потолок ожидания 30 с** в `GpuSession.end()`:
зависший command buffer больше не блокирует процесс навсегда.

Заодно проверено, что VRAM не течёт: до прогона 1287 МБ, после — 1265 МБ.

### Что сделано

- `GpuSensor` (`Sources/YumeLayersCore/GpuSensors.swift`) — читает
  `Temperature(C)`, `Core Clock(MHz)`, `GPU Activity(%)`, `Total Power(W)`
  из IORegistry-узла `IOAccelerator`. **Без root**, в отличие от SMC/powermetrics.
- `PowerController` — замкнутый контур: рабочая точка 82 °C, стоп-порог
  85 °C (93 °C — точка перезагрузки, поэтому выше 85 не уходим), аварийное
  остывание на 86 °C, шаг изменения не больше 5% за замер (это и есть
  «плавность»).
- Пользователь задаёт только потолок («мощность, %»), фактическую долю работы
  контур находит сам и держит по температуре.
- Дрейф времени шага считается по **чистому времени GPU** (`gpuMs`), а не по
  стенному: иначе собственная пауза выглядела бы как нагрев и регулятор ушёл
  бы в спираль «пауза → дрейф → ещё пауза».
- Детектор троттлинга по частоте **убран**: замер показал, что `Core Clock`
  и `GPU Activity` в PerformanceStatistics — мгновенные срезы, они скачут
  0…468 МГц на реальной нагрузке (попадают в промежутки между command
  buffer'ами). Решение по такому сигналу — реакция на шум.

`./scripts/test.sh` — **300 проверок, 0 падений**.

### Итоговый баланс: 82 / 85 / 86

Уточнение постановки от пользователя: 93 °C — это не «пик, до которого можно
дойти», а точка, на которой машина уже перезагружается. Значит 85 °C — жёсткий
потолок, а не цель, и рабочая точка должна быть ниже него с запасом на реакцию
регулятора (один замер = 2 с).

| Параметр | Значение | Смысл |
|---|---|---|
| `defaultTargetTempC` | **82 °C** | рабочая точка: выше не поднимаемся, ниже — добавляем нагрузку |
| `defaultMaxTempC` | **85 °C** | стоп-порог: выше не уходим ни при каких условиях |
| `emergencyTempC` | **86 °C** | аварийное остывание 20 с + сброс нагрузки вдвое |
| потолок нагрузки | **100%** | пользователь задаёт предел, фактическую нагрузку ищет контур |

Проверка авто-режима: `yume gpuheat 150 0` (150 с, нагрузка подбирается сама).

```
Итог: пик 76 °C, нагрузка 90%, шаг 152 → 205 мс, шагов 598
```

За 150 с непрерывной работы: нагрузка держалась на 90% (потолок), температура
колебалась 68–71 °C, **ни одного останова на остывание не было** — аварийный
порог 86 °C не достигался ни разу. Это и есть «максимум без остановок»:
три градуса запаса от рабочей точки до стоп-порога хватает, чтобы регулятор
успевал среагировать за один замер.

Отдельно стоит помнить: `Temperature(C)` в IORegistry — это край кристалла.
На этой машине он не превышает ~80–82 °C при любой нагрузке, поэтому 93 °C,
которые видел пользователь, приходят с другого датчика (вероятно SMC/hotspot),
недоступного без root. Отсюда запас в 3 °C, а не в 1: контур управляет тем
датчиком, который читает, и оставляет люфт на расхождение между датчиками.

## 12. Окно при старте: развёрнуто, но не полноэкранно

Требование: приложение должно открываться развёрнутым «до докера и до верхней
панели», как обычное приложение, — а не в нативном полноэкранном режиме,
который убирает меню-бар и Dock и создаёт отдельный Space.

Реализация — `maximizeOnLaunch()` в `Sources/YumeLayersUI/main.swift`:

```swift
private func maximizeOnLaunch() {
    guard let window = window else { return }
    guard let screen = window.screen ?? NSScreen.main else { return }
    window.setFrame(screen.visibleFrame, display: false)
}
```

`visibleFrame` уже исключает полосу меню и Dock, поэтому окно занимает ровно
рабочий стол и ничего не перекрывает. Вызывается до `showMainWindow()`, чтобы
окно не успевало мигнуть маленьким.

Проверено на запущенном приложении: контент окна 1536 × ~855 pt при экране
1536 × 960 pt — то есть ровно `visibleFrame`, меню-бар и Dock на месте.
Нативный полный экран не включается, зелёная кнопка и «Окно → Увеличить»
работают как обычно.

## 13. 99% вместо 90%: потолок снят, паузы стали условными

### Почему подняли потолок

На 90% карта держалась 68–71 °C при рабочей точке 82 °C. То есть **потолок
нагрузки и был тем, что не давало догреться** — регулятор всё время хотел
добавить, а добавить было некуда. `maxSafeDuty` поднят с 0.90 до **0.99**.

Почему не 1.00: один процент простоя оставлен WindowServer. Он композитит на
этой же GPU, и полностью непрерывная очередь рано или поздно снова доведёт до
«no successful checkins» — паники 4 ноября. При шаге 170 мс это 1.7 мс на шаг.

### Замер на 99% (`yume gpuheat 180 0`)

```
Итог: пик 78 °C, нагрузка 99%, шаг 142 → 439 мс, шагов 573
```

| Время | Температура | Мощность | Шаг |
|---|---|---|---|
| старт | 77–78 °C | 12–18 Вт | 155–227 мс |
| +60 с | 70–71 °C | 10–18 Вт | 320–440 мс |
| +150 с | 68–69 °C | 11–23 Вт | 350–580 мс |

Вывод: даже на 99% карта **не нагревается** — она сбрасывает частоту по
мощности (5–23 Вт против паспортных ~50 Вт). Нагрева нет, значит и паузы
«на остывание» ничего не охлаждают.

### Следствие: паузы только по теплу

Раньше паузы были частью расписания, а не реакцией на нагрев:

| Место | Было | Стало |
|---|---|---|
| Между эпохами | всегда `max(pauseMs, 1000)` мс | `epochCoolPauseMs()`: 0 при температуре ниже рабочей точки, половина — между точкой и потолком, полная — у потолка |
| Между батчами реконструкций | всегда `targetDuty(.nominal)` = 55% | по фактической температуре: 99% / 85% / 60% |
| На каждом шаге обучения | `floorMs = pauseMs` (250 мс) **при включённом авто** | `floorMs = 0` при авто; поле «Пауза, мс» работает только когда авто выключено |

### Найденный баг: поле «Пауза, мс» перекрывало регулятор

В `governHeat` стояло `floorMs: p.adaptiveThrottle ? pauseMs : 0`, а
`throttleDecision` берёт `sleep = max(byDuty, floor)`. При 99% расчётная пауза
на шаге — 1.7 мс, но floor поднимал её до **250 мс**. Фактическая доля работы
выходила ~40% при любых настройках, и карта не могла догреться до рабочей
точки, даже если бы хотела.

Это же объясняет, почему в реальном обучении температура была ниже, чем в
`gpuheat`: у теста floor не было вообще.

Теперь при включённом авто полом служит сама доля работы, а `pauseMs`
применяется только в ручном режиме (авто выключено) — там он и есть заданная
нагрузка.

### Проверено

`./scripts/test.sh` — **313 проверок, 0 падений**. Добавлено:

```
ok  100% → 0.99
ok  100% мощности → 99% доли работы
ok  99% → пауза меньше 2.5 мс на шаге 170 мс
ok  60 °C → паузы между эпохами нет
ok  ниже рабочей точки → паузы нет
ok  у потолка → полная пауза, но не меньше 1000 мс
ok  нет датчика → 0
```

### Что это даёт по времени

По замеру: 573 шага за 180 с — это **0.31 с/шаг** в среднем (первые полминуты
150–190 мс, потом драйвер режет частоту и шаг сползает к 350–580 мс).
Эпоха 43 187 шагов — порядка **3.8 ч**.

Для сравнения, при прежней фактической доле работы ~40% (из-за floor 250 мс)
шаг занимал ~420 мс, то есть эпоха шла бы **~5 ч**. Выигрыш есть, но он
съедается сбросом частоты по мощности — ускорить карту насильно нельзя,
она сама решает, сколько выдавать.

Если карта действительно начнёт греться, контур срежет нагрузку и темп
упадёт — но только тогда, когда это нужно, а не «по расписанию».
