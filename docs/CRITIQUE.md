# Критика плана — адвокат дьявола

Задача: раскритиковать план, предложить улучшения и итерировать, пока оценка качества не достигнет ≥95%.

## Итерация 1. Базовая критика (план сырой)

| # | Критика | Серьёзность | Исправление |

## Зафиксированные архитектурные решения (после критики)

1. **Латентное пространство — 8 каналов:** RGB-фон (3) + RGB-объекты (3) + маска (1) + карта света (1). VAE обучается отдельно.
2. **Диффузия оперирует всем латентным пространством** (8×24×24), а не тремя отдельными головками.
3. **Сборка** происходит в декодере VAE (слои суммируются с учётом маски и света).
4. **Параллельность по GPU** — расчётная: ветки можно считать на разных картах, обмен — только итоговыми латентами.
5. **Текстовое conditioning** — опционально, включается после того, как безусловная генерация работает.
6. **Реальные аниме** — используются на этапе стилизации/дообучения, а не как начальные данные.

## Итерация 4. Универсальная факторизация по экспертам (04.11.2026)

**Пересмотр масштаба.** Модель планируется обучать на максимальном объёме видео и
доводить до 30–70 ГБ весов. Значит «три маленьких U-Net по 10 МБ» — неверная
постановка. Слои нужны не для экономии на маленькой модели, а чтобы **никогда не
загружать модель целиком в VRAM 8 ГБ**: обучение и инференс факторизуются по
семантическим экспертам, активные веса поднимаются из RAM по мере надобности,
обмен между экспертами — слоями/латентами, а не весами. Одна карта (последовательно)
или несколько карт по 8 ГБ (параллельно) — один и тот же контракт.

Это **не LoRA и не дообучение чужой модели**: новая архитектурная идея —
факторизация генерации по композируемым слоям, а не по рангу весов.

### Зафиксированные решения

| # | Решение |
|---|---|
| 4.1 | Сцена = упорядоченный стек независимых слоёв (`LayerRecipe`), любой набор, любой порядок, любое число объектных слоёв. |
| 4.2 | `role` (кто произвёл: фон/объекты/свет/движение) **не привязана к семантике**. Фон-эксперт может породить фигуру, объектный — небо, фон-эксперт может сделать небо+земля+фигуры сразу. Композиция зависит только от порядка слоёв. |
| 4.3 | Фон **дополняется** объектными эксперт-слоями: `backdrop().adding(...)`. Параметры сцены генерируются в фиксированном порядке ДО рендера, поэтому добавление эксперта не меняет уже отрисованный фон. |
| 4.4 | 8-канальный ground-truth: фон RGB \| объекты RGB \| маска \| свет. Маска = **вклад объектных слоёв в итоговый пиксель** (в т.ч. при перекрытиях и полупрозрачности). Это даёт `composeLayers(flattened) == composite` **побитово для любого рецепта** — проверено на 11 комбинациях. |
| 4.5 | **Пол качества.** Чекпоинт принимается только если реконструкция кадра держит PSNR/SSIM не ниже порога и не хуже предыдущего принятого (`QualityFloor`). Диффузия предсказывает остаток поверх реконструкции, а не «рисует с нуля» — выход не может быть хуже качества, уже доказанного на входных кадрах. Обязательное сравнение с билинейным бейзлайном (§6.3 аудита). |
| 4.6 | **Движение.** На клипе статичные эксперты (небо/земля/свет) пересчитываются на ключевых кадрах, фигуры/тени — покадрово; смена плана сбрасывает кэш (`FramePlan`). Это ускорение — прямое следствие факторизации. |
| 4.7 | Масштабирование: 480p на слабой машине доказывает **архитектуру** (компонуемость, качество, скорость), а не превосходство над фронтир-моделями. После доказательства — 2K/4K на сильном железе. |

### Открытые риски (честно)

1. **Разметка реальных кадров.** Рендерер даёт идеальные слои только для синтетики.
   Как получать слои из настоящего аниме без ручной разметки — главная
   исследовательская задача проекта (варианты: self-supervised разложение через
   саму композицию, псевдо-слои от предобученного сегментатора, оптимизация
   латентов под `composeLayers` на каждом кадре).
2. **Маршрутизатор.** Кто решает, какие эксперты активировать и в каком порядке —
   отдельная обучаемая часть; её качество определяет композируемость.
3. **Накопление ошибок** в каскаде → conditioning каждого этапа на латенты
   предыдущих (уже п. 1.3) и совместный лосс при последовательном инференсе.
4. **Согласованность во времени**: объектные латенты между кадрами должны быть
   связными, иначе движение «дёргается» (см. 4.6 — кэш статики решает только фон).

## Итерация 5. VAE переведён на 8 каналов (04.11.2026)

До этого итерация 4 существовала только в рендерере: `LayeredScene` выдавал
8 каналов ground-truth, а `ConvVAEGPU` по-прежнему учился на 3-канальном RGB.
Разрыв закрыт.

### Что сделано

| # | Решение |
|---|---|
| 5.1 | `ConvVAEGPU(engine:channels:)` параметризован числом каналов. `channels = 3` — прежний путь (GUI, `convcheck`, `gpuheat`, старые чекпоинты) работает без изменений; `channels = 8` — layered-путь (`e1.ic = 8`, `d3.oc = 8`). Латент **не вырос**: сжатие 12× → 32× при том же `latentC = 16`. |
| 5.2 | **Лосс по слоям + лосс композиции.** `L = wl·MSE(8 каналов) + wc·MSE(clamp((фон·(1−m)+объекты·m)·свет), кадр) + β·KL`. Второй член обязателен: без него можно идеально выучить каждый слой и всё равно получить несовпадающий кадр. |
| 5.3 | Аналитический градиент по **всем 8 каналам**, включая маску и свет: `∂y/∂bg = l(1−m)`, `∂y/∂obj = lm`, `∂y/∂m = l(obj−bg)`, `∂y/∂l = bg(1−m)+obj·m`. Реализован и на CPU (эталон), и в Metal-ядре `layered_grad_kernel`; тест сверяет их поэлементно и конечными разностями. |
| 5.4 | `LayeredTarget` / `LayeredTargetGPU` один раз перекладывают HWC-сцену в CHW и держат таргет в VRAM весь прогон — без PCIe-копий на каждом шаге. |
| 5.5 | Бюджет VRAM (`convVAEBytesPerSample(channels:layered:)`) учитывает и рост `im2col` у `e1`, и дополнительные буферы (таргет 8n + градиент 8n + композит 3n). Старый расчёт для 3 каналов остался побитово прежним. |
| 5.6 | Несовместимость чекпоинтов честная: 3-канальный `conv.safetensors` у 8-канальной модели падает с кодом 11 и распознаётся `isIncompatibleCheckpoint` — начинаем с новых весов, а не «роняем процесс». |
| 5.7 | **Качество по собранному кадру.** `composedQuality` считает PSNR/SSIM по `composeHWC`, а не по слоям; `LayeredTrainReport.acceptedByFloor` — реальный результат ворот `QualityFloor(30 дБ / 0.90)`, без «успеха по умолчанию». |
| 5.8 | `LayeredTrainer` + CLI `layered [шаги] [мощность %]` — первый рабочий цикл, где декодер учится выдавать слои, из которых кадр собирается. Замена `makeLayeredScene` на аннотированный реальный кадр не меняет цикл. |

### Предохранитель GPU: жёсткие 90%

4 ноября 2026 машина ушла в принудительную перезагрузку: контур держал
скважность 98–99% (`maxSafeDuty = 0.98`), запас по температуре исчезал,
WindowServer не успевал отметиться. Введено:

- `safeDutyCap = 0.90` — GPU занята **не более 90% времени** ни при каких
  настройках; `effectiveDutyCeiling(powerPercent:)` применяется поверх
  температурного контура (контур может только снижать).
- `defaultGpuPowerPercent = 90` — значение по умолчанию в `Params`.
- `GpuDutyGuard` — **исполняемый** предохранитель: пауза после КАЖДОГО
  command buffer'а, включая короткие тестовые прогоны и замеры потери.
  Раньше именно короткие циклы без пауз и занимали очередь целиком.
- Аварийная температура (`emergencyTempC`) добавляет паузу поверх скважности.

`maxSafeDuty = 0.98` сохранён как физический предел и как база формулы
`dutyCeiling`; новые тесты проверяют, что 100% в интерфейсе упирается в 90%.

### Открытые риски (добавлены)

5. **Маска обучается сигмоидой, а таргет бинарен.** Это даёт мягкую маску и
   живые градиенты, но на реальных кадрах потребуется калибровка порога или
   замена на straight-through / hard-concrete.
6. **`layered_grad_kernel` и CPU-эталон предполагают кламп неактивным** внутри

7. **Синтетика ≠ аниме.** Сходимость layered-лосса на процедурной сцене
   доказывает корректность графа, но не качество на реальном видео (см. риск 1
   итерации 4 — получение слоёв из настоящих кадров остаётся главной задачей).

## Итерация 6. Реальные кадры → слои → обучение под ключ (04.11.2026, вечер)

Закрыт главный риск итераций 4–5: layered-VAE учился только на процедурной
синтетике. Теперь есть сквозной конвейер на чистом Swift (`LayerDataset.swift`):

```
MP4 → AVAssetImageGenerator → RGB-кадры → stabilizeFrames → LayerAnnotator
    → [LayeredScene] ×16 → trainLayeredVAE → чекпоинт safetensors → 7 PNG-превью
```

### Решения 6.1–6.8

- **6.1. Отрывок, а не весь ролик.** `sampleVideoTimes` берёт 2-секундный
  непрерывный кусок (отступом 3% от начала). Для 30-минутного фильма разброс
  16 кадров по всей длительности дал бы 16 разных сцен и бессмысленный
  «медианный фон» — маска различия раздувалась до **79.7%** кадра.
- **6.2. Стабилизация камеры** (`stabilizeFrames`): перебор целочисленных
  сдвигов ±8 по SAD яркости относительно центрального кадра, обрезка до общей
  области (кратно 8), отбрасывание склеек сцен. Без интерполяции — пиксели
  только переставляются, поэтому инвариант `compose(слои) == кадр`
  сохраняется (~3e-8). На панораме доля объектов упала **61.5% → 0%**
  (синтетический тест) и **79.7% → 23.9%** на реальном клипе.
- **6.3. Ёмкость латента — параметр.** `ConvVAEGPU(engine:channels:latentChannels:)`.
  `C=32` даёт сжатие 16× вместо 32× при `C=16`. `compressionRatio(channels:latentChannels:)`
  и `convVAEBytesPerSample(... latentChannels:)` учитывают ёмкость в бюджете VRAM.
  Чекпоинт `C=16` честно отвергается моделью `C=32` (код 11).
- **6.4. Косинусное расписание lr.** `cosineLR`: старт = `lr`, конец = 5%,
  монотонно, шаг вне расписания не повышает lr (важно для resume).
- **6.5. Обучение на датасете сцен.** `trainLayeredVAE(scenes:)`: сцены
  циклически чередуются, лосс усредняется по всему датасету, чекпоинт пишется
  через `saveState` (safetensors), есть отпечаток данных для честного resume.
- **6.6. Автоrelease-пул на каждом шаге.** Метал-объекты autorelease'ятся;
  без локального пула длинный прогон копит их до конца процесса. С пулом
  пик памяти 8 000 шагов — **28 МБ** (не утечка, а накладные расходы).
- **6.7. Пейсер скважности** (`GpuDutyPacer`): паузы копятся в долг и
  сбрасываются одним сном, когда ≥2 мс. Скважность остаётся ровно 90%, но
  число обращений к планировщику падает — это убирает ~20% времени.
- **6.8. Исправлен вертикальный флип PNGB.** `encodePNG` писал строки в
  CGContext (низ-вверх) как top-down: превью слоёв были перевёрнуты. Сдвиг
  строки в encode + инвариант `decode(encode(rgb)) == rgb` в тесте.

### Честный результат на реальном видео (96×72, отрывок 2 с, 16 сцен, C=32)

| Шагов | Loss | PSNR, дБ | SSIM | Пол 30 дБ / 0.90 |
|---|---|---|---|---|
| 200 | 0.27841 → 0.03313 | 22.08 | 0.975 | не пройден |
| 1000 | → 0.02212 | 24.14 | 0.984 | не пройден |
| 3000 | → 0.01470 | 26.17 | 0.990 | не пройден |
| 8000 | → 0.01111 | 27.30 | 0.992 | не пройден |
| 12000 | → 0.01110 | 27.52 | 0.992 | не пройден |

**Вывод: качество растёт монотонно, SSIM давно выше 0.90, но PSNR вышел на
плато ~27.5 дБ.** Это уже НЕ ёмкость латента (C=32), а узкое место скорости:
шаг ~25 мс, из которых ~10 мс — системное время на command buffer (см. замеры
тепло). 12 000 шагов = ~5 минут; 30 дБ потребовали бы на порядок больше
шагов, на что при текущей скорости нужно ~час.

### Открытые риски (дополнено)

9. **Плато 27.5 дБ на реальных кадрах при C=32.** Скорость шага, а не
   ёмкость, — лимитирующий фактор. Следующий шаг: батчинг нескольких сцен в
   один command buffer (или меньше `session.end()` ожиданий), чтобы позволить
   себе 50–100k шагов за то же время и добить пол 30 дБ.
10. **Стабилизация линейна по площади кадра и числу кадров** (перебор ±8 ×
    попиксельная SAD). Для 480p и 60 кадров это станет дорого; нужна грубая
    оценка сдвига на пониженном разрешении.
