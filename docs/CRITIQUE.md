# Критика плана — адвокат дьявола

Задача: раскритиковать план, предложить улучшения и итерировать, пока оценка качества не достигнет ≥95%.

---

## Итерация 1. Базовая критика (план сырой)

| # | Критика | Серьёзность | Исправление |
|---|---|---|---|
| 1.1 | «Обучение VAE на синтетике» — синтетика не репрезентативна для аниме. VAE может не перенестись | Высокая | Обучать VAE сразу на кадрах реального аниме (разбить видео на кадры и обучать реконструкции). Синтетика — только для отладки |
| 1.2 | Мини-DiT на 24×24 будет слабым; слои фон/объекты/свет в одном токене — тяжело | Высокая | Не три головки в одной модели, а **один общий диффузионный шаг для латентного пространства**, где слои представлены как отдельные каналы. Сборщик — в декодере VAE |
| 1.3 | «Слои сильно независимы» — в реальности свет влияет на цвет объектов, тени лежат на фоне. Полная независимость даст артефакты | Средняя | Слои не полностью независимы: объекты и свет обучаются с общим контекстом (cross-attention на латент фона). Параллельность вычислительная, а не семантическая |
| 1.4 | «3000–10000 кадров» мало для диффузии с нуля | Средняя | Использовать предобученную диффузию (например, Stable Diffusion 1.5 в латентном пространстве 24×24? нет — проще: дообучение LoRA на готовой SD-модели и «разложение на слои» через отдельные LoRA-ветки) |
| 1.5 | «CLIP требует интернета» — офлайн-мини-энкодер слабый | Средняя | Поддержать оба пути. На первом этапе — отключить conditioning, обучать без текста (unconditional), текстовый энкодер добавить позже |
| 1.6 | Нет оценки «работает ли вообще идея слоёв» до полного обучения | Высокая | Добавить **шаг 0: быстрое доказательство концепции** — на синтетике с 4–8 слоями, 64×64, 1–2 часа обучения. Если модель не может разделить слои — архитектура неверна, и мы узнаём это до вложения недель |
| 1.7 | Память: обучение + градиенты на 8 ГБ с 192×192 — рискованно | Средняя | Градиентная чекпоинтизация (gradient checkpointing), fp16/bf16 (на 5500M — fp16), батч 2–4. Fallback на CPU-обучение для 64×64 |
| 1.8 | Нет «распределения по нескольким GPU» — а это была главная идея пользователя | Высокая | Сделать **явный режим multi-GPU**: по веткам (фон/объекты/свет) — каждая на своей карте, обмен только латентами при сборке. В плане: P2P не обязателен — передаём через CPU |

## Зафиксированные архитектурные решения (после критики)

1. **Латентное пространство — 8 каналов:** RGB-фон (3) + RGB-объекты (3) + маска (1) + карта света (1). VAE обучается отдельно.
2. **Диффузия оперирует всем латентным пространством** (8×24×24), а не тремя отдельными головками.
3. **Сборка** происходит в декодере VAE (слои суммируются с учётом маски и света).
4. **Параллельность по GPU** — расчётная: ветки можно считать на разных картах, обмен — только итоговыми латентами.
5. **Текстовое conditioning** — опционально, включается после того, как безусловная генерация работает.
6. **Реальные аниме** — используются на этапе стилизации/дообучения, а не как начальные данные.

## Итерация 4. Универсальная факторизация по экспертам (04.11.2026)

**Пересмотр масштаба.** Модель планируется обучать на максимальном объёме видео и
доводить до 30–70 ГБ весов. Значит «три маленьких U-Net по 10 МБ» — неверная
постановка. Слои нужны не для экономии на маленькой модели, а чтобы **никогда не
загружать модель целиком в VRAM 8 ГБ**: обучение и инференс факторизуются по
семантическим экспертам, активные веса поднимаются из RAM по мере надобности,
обмен между экспертами — слоями/латентами, а не весами. Одна карта (последовательно)
или несколько карт по 8 ГБ (параллельно) — один и тот же контракт.

Это **не LoRA и не дообучение чужой модели**: новая архитектурная идея —
факторизация генерации по композируемым слоям, а не по рангу весов.

### Зафиксированные решения

| # | Решение |
|---|---|
| 4.1 | Сцена = упорядоченный стек независимых слоёв (`LayerRecipe`), любой набор, любой порядок, любое число объектных слоёв. |
| 4.2 | `role` (кто произвёл: фон/объекты/свет/движение) **не привязана к семантике**. Фон-эксперт может породить фигуру, объектный — небо, фон-эксперт может сделать небо+земля+фигуры сразу. Композиция зависит только от порядка слоёв. |
| 4.3 | Фон **дополняется** объектными эксперт-слоями: `backdrop().adding(...)`. Параметры сцены генерируются в фиксированном порядке ДО рендера, поэтому добавление эксперта не меняет уже отрисованный фон. |
| 4.4 | 8-канальный ground-truth: фон RGB \| объекты RGB \| маска \| свет. Маска = **вклад объектных слоёв в итоговый пиксель** (в т.ч. при перекрытиях и полупрозрачности). Это даёт `composeLayers(flattened) == composite` **побитово для любого рецепта** — проверено на 11 комбинациях. |
| 4.5 | **Пол качества.** Чекпоинт принимается только если реконструкция кадра держит PSNR/SSIM не ниже порога и не хуже предыдущего принятого (`QualityFloor`). Диффузия предсказывает остаток поверх реконструкции, а не «рисует с нуля» — выход не может быть хуже качества, уже доказанного на входных кадрах. Обязательное сравнение с билинейным бейзлайном (§6.3 аудита). |
| 4.6 | **Движение.** На клипе статичные эксперты (небо/земля/свет) пересчитываются на ключевых кадрах, фигуры/тени — покадрово; смена плана сбрасывает кэш (`FramePlan`). Это ускорение — прямое следствие факторизации. |
| 4.7 | Масштабирование: 480p на слабой машине доказывает **архитектуру** (компонуемость, качество, скорость), а не превосходство над фронтир-моделями. После доказательства — 2K/4K на сильном железе. |

### Открытые риски (честно)

1. **Разметка реальных кадров.** Рендерер даёт идеальные слои только для синтетики.
   Как получать слои из настоящего аниме без ручной разметки — главная
   исследовательская задача проекта (варианты: self-supervised разложение через
   саму композицию, псевдо-слои от предобученного сегментатора, оптимизация
   латентов под `composeLayers` на каждом кадре).
2. **Маршрутизатор.** Кто решает, какие эксперты активировать и в каком порядке —
   отдельная обучаемая часть; её качество определяет композируемость.
3. **Накопление ошибок** в каскаде → conditioning каждого этапа на латенты
   предыдущих (уже п. 1.3) и совместный лосс при последовательном инференсе.
4. **Согласованность во времени**: объектные латенты между кадрами должны быть
   связными, иначе движение «дёргается» (см. 4.6 — кэш статики решает только фон).
