# YumeLayers — План и чеклист

Цель: локальный генератор аниме-видео на базе обучения на собственных видео.
Схема: VAE (сжатие кадров) → диффузионная модель (генерация движения) → (опц.) текстовое управление.

---

## 1. Утверждённая архитектура параллельной генерации (из обсуждения)

**Направление выбрано: смысловые слои (фон / объекты / свет) — не нарезка картинки на куски.**

Цитаты из диалога (wangp.json):

> «Ты предлагаешь не "резать картинку на куски", а разложить сцену на смысловые слои — фон, объекты, свет — и генерировать их как отдельные проекты. Слои действительно можно считать параллельно без обмена…»

> «Этап 1 — фон (карта №1). Этап 2 — объекты (карты №2, №3…). Этап 3 — сборка.»

> «Ты хочешь единую модель, которая сама внутри понимает "вот фон, вот объекты, вот свет" и учится их создавать… ветки можно физически разложить на разные видеокарты, потому что они считают независимые вещи.»

**Что отсеяно как неверное для нашей архитектуры:**
- ❌ Нарезка картинки на квадраты/куски и склейка: швы, разрыв объектов, расхождение света/стиля.
- ❌ Параллелить шаги денойзинга между картами: диффузия — последовательная цепь Маркова.
- ❌ «Слои как в Photoshop» (LayerDiffusion-стиль) с обменом между слоями на каждом шаге: слои не независимы, аппликация/артефакты.

## 2. Чеклист этапов

### Этап A — Данные и VAE (текущий)
- [x] Извлечение кадров строго по порядку файлов/видео
- [x] Извлечение ВСЕХ кадров с частотой исходного видео (24 fps → ~43k) — без лимита 600
- [x] Кадры в памяти, без записи на диск
- [x] Параллельное извлечение (чанки) с живым прогрессом и обновлением коллажа
- [x] VAE: обучение на GPU (Metal), NaN-защита, авто-пауза при перегреве
- [x] Термо-монитор: проверка thermalState каждые N шагов + прогрев по замедлению шагов
- [x] Чекпоинты в общепринятом бинарном формате **safetensors** (без JSON)
- [x] Реконструкции (режим «Реконструкция» в UI)
- [x] Использование второй GPU (Intel UHD 630) для параллельной генерации реконструкций
- [ ] Обучение VAE на полном наборе (~43k кадров) и оценка качества реконструкций

### Этап B — Диффузионная модель (следующий)
- [ ] **Сохранение клипов движения**: кадры хранятся с меткой источника (файл/серия) и строгим порядком внутри клипа — фундамент для обучения временным окнам
- [ ] Обучение диффузии в латентном пространстве VAE (60×64×64 → меньше, по результатам A), на окнах из N подряд идущих кадров клипа
- [ ] Продолжение видео с последнего кадра (seed-продолжение)
- [ ] Интерполяция между двумя кадрами: А → Б + длительность → N промежуточных кадров
- [ ] (позже) Перенос движения: выделение поз из клипа → генерация другого персонажа под эти позы
- [ ] Чекпоинт диффузии в safetensors

### Этап C — Смысловые слои (параллельная генерация на слабых картах)
- [ ] Прототип: отдельные ветки «фон» и «объекты» внутри одной модели
- [ ] Кондиционирование объектов на готовый фон (одна картинка-условие)
- [ ] Сборка: фон + объекты + свет → итоговый кадр
- [ ] Раскладка веток по разным GPU (механизм второй GPU уже есть)
- [ ] Тест: 2 слабые карты генерируют один кадр быстрее/параллельно

### Этап D — Интеграция и использование модели
- [ ] Инструмент генерации (аналог WanGP для нашей модели): локальный API/CLI/UI поверх готовых весов
- [ ] Экспорт/чтение весов в safetensors сторонними инструментами (общепринятый формат)
- [ ] Текстовое управление (опционально): капшены → текстовый энкодер → условие

---

## 3. Замечания по интеграции (честно)

- **WanGP** — это CUDA/ROCm-экосистема (Python/PyTorch, NVIDIA/AMD RDNA2+). Наша модель — нативный Swift/Metal. Напрямую «положить» нашу модель внутрь WanGP нельзя.
- Реалистично: наш инструмент генерации (UI/API/CLI) сам использует нашу модель; веса хранятся в safetensors — общепринятом формате, поэтому их можно читать и конвертировать и из другого софта.
- Схема «слабая карта = один слой» даёт выигрыш именно в сценарии с несколькими картами (как X99 + 2×5060 Ti или Radeon + Intel UHD).
