### Сделано (сначала падающий тест, потом код)
- **C4 — настоящий VAE.** Энкодер e3 выдаёт `2·C` каналов → `split2` → `mu`/`logvar`;
  `σ = exp(0.5·clamp(lv,-10,10))`; `z = mu + σ·ε`; потеря `MSE + β·KL`;
  обратный проход через перепараметризацию и KL (`vae_grad_kernel`).
  Новые ядра: `fma`, `exp`, `addconst`, `exphalf`, `split2`, `merge2`, `kl_reduce`,
  `randn` (детерминированный hash-гаусс), `vae_grad`.
- **C1** — `accGrads` инициализируется `session.copy`, а не `addInPlace` поверх мусора.
- **C2** — `convVAEBytesPerSample` (466 МБ на кадр 854×480) + `activationBudgetBytes`
  (30% рабочего набора). Пачка на 8 ГБ = 8, не 16. Пул кадров 60% + активации 30% ≤ 100%.
- **C3** — `allocationFailureMessage`: внятный текст при OOM вместо `nil`-краша.
- **C5** — `ConvVAEGPU.latentC = 16` (сжатие 12× вместо 3×). Одна константа меняет
  ширину e3 (2·C) и вход d1 (C).
- **H5** — `markProcessedFrames` ставит галочку ✓ после реконструкций (раньше никогда).
- Инициализация весов: `SplitMix64(seed:)` + He `√(2/fanIn)` вместо `Float.random`
  без seed и масштаба `×0.2` (сигнал затухал, часть ReLU умирала на старте).
- `convcheck` теперь дифференцирует `vaeLoss` (MSE+β·KL), а не только MSE.

## Перезагрузка из-за перегрева GPU (10:10 → 10:19)

### Что случилось
Паника `userspace watchdog timeout: no successful checkins from WindowServer
in 120 seconds` + `com.apple.driver.watchdog` в backtrace. Это НЕ сбой шейдера:
WindowServer композитит на той же дискретной GPU (Radeon Pro 5500M), что и
обучение; когда GPU перестала отвечать, оконный сервер не отметился за 120 с
и watchdogd выключил машину.

Хронология: 10:02 старт → 0.20 с/шаг → 10:09 уже 0.80 с/шаг (троттлинг 4×)
→ 10:10:35 последний чекпоинт (шаг 1500) → тишина → 10:19:29 reboot.

### Корневая причина
`pauseMs` (250 мс) применялся ТОЛЬКО на границе эпохи:
`if ep < p.epochs - 1 { Thread.sleep(pauseMs/1000) }` — а эпоха это 43 187 шагов.
Внутри эпохи стоял жёсткий `Thread.sleep(0.03)`. Скважность GPU ≈ 85% на часы.
`thermalGuard` поднимал `pauseMs`, который нигде не применялся → авто-троттлинг
не срабатывал ни разу.

### Исправление
- Новый `Sources/YumeLayersCore/ThermalGovernor.swift` — чистые функции:
  `heatLevel`, `targetDuty`, `dutySleepMs`, `updateStepBaseline`, `throttleDecision`.
  Скважность ≤ 55% / 45% / 30% / 12% по уровню нагрева. Признак нагрева — не
  только `ProcessInfo.thermalState` (запаздывает), но и дрейф времени шага
  относительно скользящего МИНИМУМА (среднее съезжает вместе с троттлингом).
- Пауза теперь на каждом шаге, в конце тела цикла; `gpuMs` берётся из
  `session.end()` (forward/backward + Adam суммируются).
- `GpuSession.end()` ждёт с потолком `gpuDeadlineSeconds = 30` вместо
  `waitUntilCompleted()` (тот при зависании GPU не возвращается никогда).
- Реконструкции: батч 16 → по бюджету активаций (~466 МБ/кадр), та же скважность.

### Замеры
- `scripts/test.sh`: 272 проверки, 0 падений (было 261), новый раздел
  «Термо-регулятор GPU».
- Ожидаемый темп: 310 мс/шаг при батче 1 (эпоха ≈3.7 ч); при батче 4 —
  ≈375 мс на кадр, т.е. быстрее и холоднее одновременно.

### Грабли

## Цель по температуре: 85 °C, потолок 89 (12:10)

Пользователь требует работать на грани троттлинга, а не «на 65%».

Замер авто-режима (90% нагрузки, 120 с): пик 76 °C, дальше температура
**падала** до 66-67 °C, мощность 5-17 Вт, шаг 146 → 216 мс.
Вывод: драйвер режет частоту по мощности раньше, чем карта греется.
Датчик `Temperature(C)` на этой машине выше ~80 °C не поднимается даже
при 90% нагрузки — цель 85 °C по нему недостижима.

Замер при 85% нагрузки 50 с: край 80-82 °C, 41-47 Вт, CPU_Speed_Limit 93→27.

Итоговые настройки:
- `defaultTargetTempC = 85`, `defaultMaxTempC = 89`, `emergencyTempC = 91`
  (перезагрузка случалась на 93).
- `gpuPowerPercent = 100` → потолок скважности 0.90.
- Защита по просадке шага: `heatLevel >= .hot` → −10% нагрузки, не чаще
  раза в 2 мин, пол 0.50 (чтобы не уехать в бесконечное замедление).
- `yume gpuheat <сек> 0` — авто-режим (контур), `<сек> <процент>` — фикс.

## 99% нагрузки и паузы только по теплу (13:59)

Пользователь: «нагрузка была маленькая — надо 99%». Поднял `maxSafeDuty`
0.90 → **0.99** (1% оставлен WindowServer, иначе снова watchdog).

Замер `yume gpuheat 180 0` на 99%: пик 78 °C, дальше 68–70 °C, мощность
5–23 Вт, шаг 142 → 439 мс. **Карта не греется даже на 99%** — драйвер режет
частоту по мощности раньше, чем появляется тепло.

**Найден баг:** `governHeat` передавал `floorMs: p.adaptiveThrottle ? pauseMs : 0`
(250 мс). `throttleDecision` делает `sleep = max(byDuty, floor)` — то есть
поле «Пауза, мс» перекрывало регулятор: при 99% пауза 1.7 мс поднималась до
250 мс, фактическая нагрузка ~40%. Исправлено: при авто `floorMs = 0`,
`pauseMs` работает только в ручном режиме.

Паузы сделаны условными (только по температуре):
- между эпохами — новая чистая функция `epochCoolPauseMs(tempC:pauseMs:...)`:
  0 ниже рабочей точки, половина между точкой и потолком, полная у потолка;
- реконструкции — вместо фиксированных 55% берут текущую температуру
  (99 / 85 / 60%).

Тесты: 313 проверок, 0 падений.

**Правило на будущее:** любая пауза в этом проекте — тепловой инструмент,
а не часть расписания. Если карта холодная, пауза = 0.
